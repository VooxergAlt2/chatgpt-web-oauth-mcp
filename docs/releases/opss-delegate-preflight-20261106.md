# ACP preflight, durable result ownership and cleanup

Cycle started 2026-11-06; validation continued on 2026-11-07 Europe/Moscow. Baseline `262e781bc6aa28f07e64cd3ec6188efa6cbf8b29`; initial implementation head `72caf78`; final code head `0ed6f19`.

## Implemented

- Optional `verification_preflight_commands` for ACP code tasks: at most four nonempty commands, each at most 4096 UTF-8 bytes. They run in the same fresh read-only, network-isolated verification namespace as final checks, before constructing the native sandbox or runner. The aggregate budget is at most 30 seconds, inside the original deadline with the final verification reserve retained. Failed, cancelled or expired probes prevent inference and promotion. No dependency guessing, baseline behavioral tests or host fallback is introduced.
- Exact ordered preflight results are bound separately in the hash-bound verification receipt. Passing preflight never substitutes for final behavioral acceptance. Omitted/empty probes preserve existing task and contract identities. Nonempty probes are rejected for CLI, explore and proposal tasks. Guide version is 1.13.
- Verification threads now drain their owned process groups before private workspace cleanup, including repeated task cancellation. The same helper covers both preflight and final verification. Telemetry preserves preflight elapsed time in total setup accounting. Final command admission, worker and receipt limits agree at 16 commands / 8192 UTF-8 bytes, and reject NUL before inference.
- Start, terminal and queued-cancellation metadata retain the canonical logical owner and ACP resume context. Result ownership reads indexed server metadata independently of the bounded eight-result consumed inbox. Historical ACP metadata without a raw owner is accepted only after canonical private session identity, reference and exact delegate-turn validation. Foreign, conflicting, corrupt or missing proof remains denied.
- Successful removal of the current session's worktree relocates its default cwd to a surviving registered repository. Compare-and-set preserves a concurrent cwd change; the checkpoint transaction replaces only matching cwd fields and preserves job/delegate evidence. Other sessions and explicit invalid cwd arguments are unchanged. The pre-existing stale default from the prior cycle was repaired through `set_default_cwd`.
