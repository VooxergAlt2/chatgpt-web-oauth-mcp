# ACP на задачах сопровождения: измерения после R1

Цель — решить, во что вкладывать следующий релиз: навигация по C#, передача уже принятого результата между задачами или координация общей среды. Сначала собираем наблюдения на обычных задачах. Ответ агента проверяет управляющий по исходникам, тесту или рабочему MCP.

## Как вести выборку

Для первых пяти последовательных подходящих задач (исследование, ревью или небольшое изменение в одном-двух файлах) до запуска записать исходный commit, вопрос, scope, ожидаемый результат, независимую проверку, лимит инструментов и времени. Включать отказы, таймауты, повторные запуски и отклонённые результаты в общий эпизод. Синтетические нагрузочные прогоны вести отдельно.

Из `delegate_status` взять ID, роль, аккаунт, модель, время постановки, старта и завершения, доступный счётчик инструментов. Из `delegate_packet` взять уровень проверки, подтверждение записи, состояние исходников и видимость повторов. Вручную добавить время независимой приёмки, число вмешательств, результат и основание. Длительность работы агента и время от постановки до принятия учитывать раздельно. Если метрика отсутствует, писать «нет данных». При неполном native-наблюдении ноль повторов gateway не заменяет полный счётчик повторных чтений. В журнал не копировать токены, приватные запросы или содержимое рабочих проектов.

После первых пяти эпизодов проверить полноту измерений и назвать конкретные источники потери времени. Для сравнения режимов зафиксировать одинаковые исходные снимки, критерии, модель и суммарный бюджет, включить контрольные задачи без дефекта и повторить на сопоставимых задачах. Считать принятые результаты, суммарное время на них с учётом неудач, долю отклонений и вмешательства. Решение о разработке R2 привязать к воспроизводимому ограничению на реальной задаче.

## Как сравнивать расход квот

Для следующей пары запусков основной показатель — сколько квоты большой модели расходуется на одно принятое решение. На серии задач также считать, сколько одинаково проверенных решений удаётся выпустить до исчерпания ограничивающей квоты. Допускается больший суммарный объём токенов, если управляющий расходует меньше своего лимита, у исполнителей есть запас и сохраняется качество.

- Сравнить самостоятельное решение большой моделью с решением через Flash на одном исходном снимке и с одной независимой приёмкой. Обе стороны стартуют без решения другой стороны. Учитывать постановку, чтение ответов, повторы, ручные исправления и финальную проверку. Показывать число принятых и всех поставленных задач.
- До и после каждого режима сохранять свежесть наблюдения, аккаунт, группу моделей, окно, остаток в процентах и момент сброса. Считать разницу в процентных пунктах отдельно по каждому сопоставимому окну. При сбросе, параллельной посторонней работе, устаревшем или слишком грубом измерении помечать расход как неизвестный. Одно задание может затрагивать одновременно короткое и недельное окна.
- Сохранять отдельно расход большой модели и нагрузку на каждый аккаунт делегатов. На AGY видны окна группы Gemini Models на 5 часов и неделю. Публичная квитанция Flash с total_tokens сама по себе не определяет величину списания. При отсутствии прямого замера квоты управляющего приводить доступную оценку работы управляющего с явной границей измерения. Денежный тариф и фиксированный курс обмена токенов для этой проверки не требуются.

### Почему полевой пилот показал максимум двух одновременных ACP

Для восьми ACP-задач с указанными выше ID (два первых эпизода, четыре анализа/правки из эпизодов 4–5 и два контроля `57e8b9074abf`, `8d30a74c7d91`) сверены времена подачи, фактического старта и завершения. Все восемь работали на AGY1 и стартовали за 11–12 мс после подачи. Одновременно выполнялись максимум две. Третьей ожидающей задачи в этой выборке не было. Отдельный приёмочный читатель `17b57e684a0f` провёл в очереди 41,776 с, поскольку был явно привязан к завершению родительской группы.

| Ограничение рабочего сервиса | Проверенное значение |
|---|---|
| Один репозиторий с общим Git-каталогом | До 4 анализов, 2 ревью и 3 реализаций по разным worktree |
| Один worktree | До 4 читателей суммарно либо 1 эксклюзивный writer |
| Все проекты сервиса | До 8 читателей и 4 writer |
| Каждый аккаунт AGY1, AGY3, AGY2 | До 4 одновременных reader и writer суммарно |

Значения ролей и аккаунтов возвращают рабочие `server_info` и `delegate_harnesses`. Глобальные лимиты и общий предел worktree сверены с параметрами процесса и конструктором планировщика для `db479e0`. При включённом выборе аккаунта по свободным слотам автоматическое разбиение одиночной задачи планировщиком отключено.

Для независимых вопросов управляющий заранее выделяет разные области и отправляет по одному `delegate_task(kind="explore", work_role="analysis", backend="auto", wait_seconds=0)`; после постановки всех задач ожидает их по ID. Для независимого ревью назначает `work_role="review"`. Автомаршрут последовательно заполняет AGY1, AGY3 и AGY2. Явный `backend="acp"` требует указать `harness` и закрепляет задачу за аккаунтом. `delegate_batch` в этой версии создаёт CLI-сессии на одном аккаунте. Зависимость между задачами нужна, когда последующей действительно требуется завершение предыдущей.

## Предлагаемый первый срез R2

1. **Определить принадлежность файла выбранной сборке C#.** В запросе фиксировать commit, решение или проект, Configuration, Platform и при необходимости TargetFramework. При входе через решение учитывать по каждому проекту `ActiveCfg` и `Build.0`. В Astra конфигурация решения `Release|Any CPU` выбирает `Release|x64` для DeviceAddressing.
2. **Вернуть проверяемый ответ.** Сохранить идентификатор SDK, выбранный проект и конфигурацию, источник списка `Compile`, фактически включённые файлы и причину неполного результата. Разделить включение в проект, реализацию интерфейса и runtime-выбор DLL. При недоступных SDK, imports или reference packs показать неопределённость.
3. **Прототипировать на фиксированном снимке.** На gip-core SDK 8.0.425 / MSBuild 17.11.48 командой `dotnet msbuild Astra/Astra.csproj -p:Configuration=Release -p:Platform=AnyCPU -getItem:Compile` возвращает 24 файла оболочки. В отдельном Astra.Logic — 5. Время прямой оценки одного проекта в пробах Debug/Release — 262–272 мс. В обычном PATH Opss команда отсутствует, в пилоте использован проверенный абсолютный путь. Для рабочего инструмента нужен настроенный SDK и изолированная оценка разрешённых снимков без сети, restore и запуска сборочных targets. Учитывать imports и property functions.
4. **Приёмка прототипа.** Проверить включённый и исключённый похожие файлы, проект вне решения, платформенное переназначение, условный Compile, link/glob, несколько целевых фреймворков и отсутствующий import. Сравнить с текущей текстовой трассировкой на тех же вопросах: ошибки достижимости, полное время до принятого ответа, количество открытий. Только затем выбирать объём Roslyn-навигации.

**Передача проверенного результата** остаётся отдельным кандидатом R2. Для неё нужен opt-in контракт с владельцем, scope, точным digest и явным решением о приёмке. Проверки должны охватывать отклонённые, устаревшие и отменённые результаты, повтор и restart. Действующий барьер групп обслуживает порядок выполнения. Для расширения координации общей среды пока нет измеренного конфликта из этих пяти задач.

### Приёмка изменений Opss

Для интегрированного кода `9f88166` прошли compile, 51 адресный тест, diff --check и полный набор (2236 passed, 3 skipped, 18 subtests passed). HTTP-проверка с двумя владельцами и контролируемым исполнителем воспроизводила ошибки на `52f14fb`, затем прошла на исправлении для успешной и упавшей родительских групп. ACP-ревьюер `8d30a74c7d91` исчерпал бюджет 8 вызовов без заключения. Независимый ревьюер проверил допускающие ветви под блокировкой. Внутренний Python-вызов с group_id может встретить уже завершившуюся группу при позднем повторе; публичные инструменты этот аргумент не передают.

Committed diff impact обработал 20 изменённых символов за две страницы. Проверены импорты модуля подсказок; статический анализ содержит неразрешённые места вызовов. При параллельной приёмке вне пяти исходных эпизодов дважды исчезал контейнер прогретого графа. После завершения suite повторный канонический прогрев дал query_ready. У штатного тестового HTTP-сервера обнаружен путь от shutdown до удаления контейнеров по общей Docker-метке. Точный инициатор каждого из двух сигналов не установлен. Независимые работающие серверы с включённым графом требуют разграничения владельцев при cleanup, capacity, повторном создании и GC.

На двух временных state_dir с подставным Docker подтверждено: остановка A выбирает для удаления контейнеры A и B. Реальный Docker в этой проверке не использовался. Общий pytest теперь получает отдельный state_dir и выключенный Code Graph; тесты worker и graph явно подставляют исполнителя. Критерий дальнейшего исправления production — два включённых сервера с одним graph_id в разных каталогах живут независимо при shutdown, очистке, повторном запуске и вытеснении по лимиту. Для старого контейнера установить владельца по его монтированию; при неоднозначности пропустить удаление.

Финальный прогон на 2b32ddf: 2237 passed, 3 skipped, 5 warnings, 18 subtests passed за 234,71 с. Перехватчик docker в PATH не зафиксировал вызовов. До и после полного набора совпали Docker ID и время старта действующего query runtime, code_graph_status подтвердил query_ready. Отдельная выборка graph/HTTP дала 132 passed с таким же перехватчиком. Автономная матрица MSBuild прошла в рабочей копии.
